EFI BITCom email sign-in and private workshop storage

The public workshop remains available to guests. Guest state lives in browser
storage and can be exported as JSON. Confirmed participants can sync task
completion, reading position, workbook answers and scratchpad.

Deployment
- The ept_api BITCom module is deployed with the existing EPT Render service.
- BITCOM_REGISTRATION_ENABLED=true enables the module after its private tables
  initialise and SMTP settings are present. EPT startup can continue if BITCom
  setup fails. GET /api/bitcom/registration/status reports the workshop status.
- The extension uses the existing EPT PostgreSQL connection to Supabase and
  the EPT SMTP relay. Supabase Auth settings and EPT email templates are separate.
- BITCom mail uses the relay's existing mailbox with the display name EFI
  BITCom. It includes a clickable HTML link and a plain-text alternative.
- Set the public workshop configuration to enabled:true once the live route is
  available. The API URL and enable flag are public. Credentials stay on Render.

Access and storage
- Links expire after 20 minutes. Confirming requires the matching address and
  consumes the link. Only hashes of the link token and receipt are stored.
- The browser receives a workshop-scoped receipt for 12 hours, or 30 days with
  the participant's explicit choice. Server work is scoped to that account.
- A separate revision on progress and workbook prevents stale writes from
  replacing newer work. The browser retains pending work for JSON export.
- After confirmation, /profile assigns an unused genomic FASTA case. /load and
  /save scope work to that case. /new-run requires all 37 tasks to be saved as
  complete and leaves the preceding workbook available for reading and export.
- Existing work that names one exact genomic FASTA is carried into that case.
  Other previous work remains available in the profile under Previous workshop
  work. The original saved-work rows remain available to the migration.
- PostgreSQL row-level security is enabled for all BITCom tables. Public,
  anon and authenticated grants are removed. The server holds the database
  connection. The API never exposes a participant list or Supabase credentials.
- The sign-out action revokes the browser receipt and clears signed-in cache.
  Participant removal should delete the corresponding saved work, receipts and
  registration in one transaction, along with any pending link for the address.

Verification
- Run the BITCom unittest suite using the EPT backend dependencies. It uses an
  isolated SQLite database and simulated SMTP.
- Run the JavaScript tests for guest mode, confirmation, backup and conflicts.
- Test production with the organiser's approved address. Verify inbox receipt,
  confirmation, saving, sign-out and retrieval in a fresh session.
- The SMTP request limit is 120 per hour and one per address per minute.
  The relay can impose additional limits. A delivered test email does not
  establish delivery to every workshop participant.
